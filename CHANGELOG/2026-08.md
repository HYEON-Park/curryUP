### 배치 재배치(자동 재실행) 기능 추가 + 재배치 실패 시 OS 알림
- 모든 스케줄 배치(notify · 종료공고 점검 · scrape · write-documents)가 실패하면 5분 뒤 1회 자동 재실행(재배치). 성공·정상 스킵(대상 없음)은 재시도하지 않는다.
- 원본·재배치가 모두 실패(더블 실패)하면 **OS 알림**으로 통지 — notify 배치가 쓰는 `notifyWithLink`(osNotifier)를 재사용하고 문구만 실패용으로 변경(클릭 시 대시보드로 이동).
- 공용 래퍼 `withScheduledRetry(jobName, run)`로 구현. 반환된 `RunRecord.status`로 실패 판정 후 `setTimeout` 5분 뒤 재실행. 4개 배치의 cron 핸들러에만 적용(관리자 수동 실행·catch-up 제외). 새 저장 파일·runLog 스키마 변경 없음(재배치도 스케줄 실행 레코드로 runLog에 남음).
- 한계: 재시도는 인메모리 `setTimeout`이라 5분 대기 중 서버가 재시작되면 그 재시도는 유실된다(실패가 발생한 경우에만 해당).
- 신규: `backend/src/scheduler/scheduledRetry.ts`
- 수정: `backend/src/scheduler/scrapeJob.ts`, `backend/src/scheduler/notifyJob.ts`, `backend/src/scheduler/closedCheckJob.ts`, `backend/src/scheduler/writeDocumentsJob.ts`

- 본문 백필을 **채택 확정 시점**에 배선: `runScrapeAndMatch`에서 공고가 모든 필터(매칭·마감·숨김·영구삭제)를 통과한 직후에만 `fetchPostingBody`를 호출해 요청 수 최소화. 잡코리아는 목록 수집 단계에서 이미 `postingBody`를 채우므로 `!posting.postingBody` 조건으로 자동 스킵
- 공고 상세 화면의 **공고 탭을 항상 노출**하도록 변경(이전엔 `postingBody`가 있을 때만 노출). 원문이 없으면 수집 시 확보한 실제 필드(직무·근무지·마감·요구 연차·스킬 칩)만으로 `PostingSummary`를 렌더 — 원문 창작 없이 "원문 미수집" 안내와 함께 표시
- 검증: 백엔드 `tsc --noEmit` 통과(에러 0)
