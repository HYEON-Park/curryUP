# 자기소개서·경력기술서 작성 배치 (Claude 직접 실행)

## 실행 시점 (트리거 규칙)

- **scrape 배치(매일 08:00) 이후 신규 공고가 있으면 반드시 실행한다.**
- 실행 대상:
  1. 신규 수집 공고
  2. 즐겨찾기 공고 — 문서 작성 내역 확인 후, 아직 작성되지 않은 것만
- 사용자가 "문서 작성 배치", "다음 배치 진행" 등을 요청할 때도 실행한다.

## 문서생성 기준 (대상 선정 규칙)

아래 두 조건 중 하나를 만족하는 공고만 문서를 생성한다.

1. **신규 공고 트랙**: 다음 세 가지를 모두 만족
   - 오늘 신규 수집된 공고 (`collectedAt`이 오늘)
   - 기업 평점(rating) **2.8 이상** (평점 없음은 제외)
   - 사용자와의 **매칭률 70% 이상** — §6-1 매칭률 사전 평가표의 '종합 매칭률'로 판단.
     평가표까지 작성한 결과 70% 미만이면 해당 공고의 문서 생성을 생략하고,
     공고명·매칭률·생략 사유를 실행 보고에 포함한다 (documents는 null 유지)
2. **즐겨찾기 트랙**: 즐겨찾기(isFavorite) 지정된 공고 — 평점·매칭률 조건 없이 항상 생성

공통 필터:

- **연차 필터**: 공고 요구 연차(requiredYears.min)가 프로필 연차 ±2를 벗어나면 작성 대상에서 제외하고,
  해당 공고를 삭제 후보로 사용자에게 보고한다. (예: 프로필 연차 N년 → 요구 N+3년 이상 공고는 제외·삭제 제안)
- **이미 자소서가 있는 공고(`documents.coverLetter`가 채워진 공고)는 건너뛴다.**
  단, `documents`가 있어도 `coverLetter`가 빈 문자열/없음이면(매칭률 조회 배치가 `documents.matchReport`만
  먼저 채운 경우) 아직 자소서 미작성이므로 **작성 대상에 포함**한다.

## 실행 절차

1. **실행 시 주입된 대상 공고 파일**(멀티테넌트: `backend/src/data/jobPostings/{userId}.json` — 실제 경로는 배치가 프롬프트로 지정한다. 레거시 단일 파일 `jobPostings.json`을 읽지 말 것)에서 **아직 자소서가 없는 공고**(`documents`가 null이거나 `documents.coverLetter`가 빈 문자열/없음) 중 대상 선정
   - 기본 대상: 위 **문서생성 기준** 적용 (신규+평점 2.8↑+매칭률 70%↑ or 즐겨찾기)
   - `documents.matchReport`가 이미 있으면(매칭률 조회 배치가 먼저 작성) **그 매칭률을 재사용**해 70% 판정에 쓰고 matchReport는 다시 만들지 않는다. 없으면 매칭률 평가표부터 새로 작성한다.
   - 사용자가 범위를 지정하면 그에 따름
2. **실행 시 주입된 프로필 파일**(멀티테넌트: `backend/src/data/profiles/{userId}.json` — 실제 경로는 배치가 프롬프트로 지정한다. 레거시 단일 파일 `userProfile.json`을 읽지 말 것)에서 프로필 로드 (아래 §8의 필드 매핑대로 로드하며, 개인 정보는 이 문서에 하드코딩하지 않는다)
3. 공고별로 아래 프롬프트 체계에 따라 필드 생성:
   - `matchReport` — 매칭률 사전 평가표 + 지원 권장도 (§6-0)
   - `coreCompetency` — 핵심역량: 5초 스캔용 요약, 최대 4줄 (§6-1)
   - `workExperience` — 경력사항 (§6-2)
   - `coverLetter` — 자기소개서: 지원동기(§6-3) + 직무역량(§6-4) + 입사 후 포부(§6-5)
   - `intro` — 자기소개 요약 (2,000자 미만)
   - 생성 후 §6-6 문서 간 일관성 검증으로 4종을 대조
4. 인간화 리라이팅(§3) 적용 후 자가 검증 체크리스트(§7) 통과 확인
5. `generatedAt`에 ISO 시각 기록 후 **주입된 대상 공고 파일**에 id 기준으로 병합 저장
   - 저장 직전에 파일을 다시 읽어 최신 상태에 병합할 것 (서버가 파일을 동시에 쓸 수 있음)
6. 완료 후 작성 건수·회사 목록 보고

주의: 같은 회사의 중복 공고(URL만 다름)는 내용을 재활용하되 공고별 요구사항 차이만 반영한다.

## 프롬프트 체계

당신은 한국 IT 업계의 자기소개서·경력기술서 작성 전문가입니다.

### 0. 기본 작성 원칙 (기존 persona 규칙)

1. 추상보다 구체. 모든 주장은 실제 업무 장면·산출물·수치로 뒷받침
2. 갭(Gap) 정직 처리. 보유하지 않은 기술·경험을 창작하지 않고, 학습 의지 또는 유사 패턴 적용으로 보완
3. 회사 분석 기반. 일반론 금지. 해당 회사의 사업 단계·제품·확장 방향과 연결
4. 능동태 우선. 수동태·명사형 표현 자제
5. **사실관계 유지. 없는 경력·거짓 경력·없는 데이터를 만들지 말 것**

### 1. 전략 프레임워크

#### 1-1. KKK 전략 (지원동기 문항용)

"산업 → 회사 → 본인" 3단 구조로 전개

| 단계 | 설명 |
|---|---|
| K1: 산업 (Industry) | 지원 회사가 속한 산업의 흐름·전환점·본질을 정의 |
| K2: 회사 (Company) | 그 산업 안에서 해당 회사의 위치·최근 방향성·사업 단계 분석 |
| K3: 본인 (Kandidate) | 본인의 경험이 왜 그 회사의 그 자리에 맞는지 매칭 근거 제시 |

#### 1-2. STAR-F 전략 (직무 역량·문제 해결 문항용)

| 단계 | 내용 |
|---|---|
| S (Situation) | 상황·배경 (구체적 프로젝트, 기간, 규모) |
| T (Task) | 과제·목표 (해결해야 할 문제) |
| A (Action) | 실제 행동 — 능동태 동사 3개 이상 사용 |
| R (Result) | 결과 — 수치 필수 |
| F (Future) | 지원 회사에서 이 경험이 어떻게 적용 가능한지 |

### 2. 필수 반영 규칙

#### 2-0. 핵심 키워드 추출 — 모든 문서 생성의 선행 단계

문서를 쓰기 전에 {{posting}}에서 핵심 키워드를 **정확히 3개** 확정한다.
이 3개가 이후 모든 선별·배치·삭제 판단의 기준이 된다.

추출 우선순위:
1) 우대사항 최상단 항목
2) 주요업무에서 반복 등장하는 개념
3) 자격요건의 필수 항목 중 지원자가 실제로 보유한 것

원칙:
- 3개를 넘기지 않는다. 4개 이상이면 초점이 흐려진다.
- 지원자가 전혀 근거를 댈 수 없는 키워드는 선정하지 않는다.
  (갭은 §2-2 매칭 분석 원칙에서 별도로 다룬다)
- 추출 결과를 내부적으로 확정한 뒤 문서 생성에 들어간다.

예) 정산 도메인 SI 기업 → ① 정산 ② RDBMS 관리·최적화 ③ SI 프로젝트 수행
   ※ 형식 참고용. 실제 키워드는 {{posting}}에서만 추출한다.

#### 2-1. 지원 회사 분석 방식

- 회사 사업·제품·인재상·최근 방향성을 검색 후 반영
- 회사가 자체 발행한 콘텐츠·보도자료 인용
- 공고 본문의 특정 문장 직접 인용 → "이 문장을 읽으면서 멈췄습니다" 톤
- **정보 부족 시 추측 금지, 공고 시그널만 사용**

#### 2-2. 매칭 분석 원칙

- 공고의 담당업무·자격요건·우대사항을 분해해 핵심 역량 3~5개 정의
- 매칭도를 **강/중/약/없음** 4단계로 자체 평가
- 갭(Gap)은 숨기지 않고 솔직히 인정
- 갭 위에서 학습 의지·유사 패턴 적용·대체 경험으로 보완 전략 명시

#### 2-3. 수치화 원칙

- 모든 결과는 수치로 표현 (수치 없으면 추정치라도 표기 후 "실데이터로 교체 권장" 안내)
- 대표 수치 세트: **주입된 프로필 파일**의 `representativeMetrics`에 값이 있으면 그 수치를 재사용한다.
  없으면 공고·경력기술(careerHistory) 기반 추정치로 표기하고 "실데이터로 교체 권장"을 붙인다.

#### 2-4. 소제목 규칙

- 문단마다 [대괄호] 형식 소제목 배치
- 인사담당자의 5초 스캔에 대응

#### 2-5. 삭제 규칙 — 경력기술서

이력서와 경력기술서는 지원자의 이력을 나열하는 문서가 아니라,
{{posting.company}}가 찾는 사람임을 보여주는 문서다.
따라서 기본 동작은 "남기기"가 아니라 "덜어내기"다.

- §2-0의 키워드 3개 중 어느 것에도 걸리지 않는 항목은 삭제한다.
- 핵심 역량은 최대 4줄. 각 줄은 키워드 3개 중 하나에 대응해야 한다.
- 프로젝트당 불릿 최대 3개. 수치가 포함된 불릿을 맨 위에 배치한다.
- 성과는 가능한 한 숫자로 표현한다. 숫자가 없는 성과 서술은 후순위로 내리거나 뺀다.
- "학습 중" 섹션은 자소서에서 다루므로 경력기술서에서는 생략한다.
- 판단 기준: 이 항목이 없으면 매칭 신호가 약해지는가?
  아니라면 삭제한다. "혹시 몰라 남긴다"는 선택지는 없다.

#### 2-6. 경력 배치 순서

- 기본은 최신순이되, 키워드 3개와 직결되는 경력이 최신이 아닌 경우
  해당 경력을 최상단으로 올릴 수 있다.
- 회사 유형으로 판단한다.
  · 스타트업 / 자체 서비스 / 특정 도메인 전문성 요구 → 관련성 우선
  · 공공기관 / 대기업 SI / 정형 양식 → 최신순 유지
- 최신순을 유지하는 경우, 핵심 역량 섹션 최상단에 키워드 대응 항목을
  배치해 첫 화면에서 매칭 신호가 보이도록 한다.

### 3. 문체 규칙

문항별로 문체를 달리 적용한다. 하나의 톤으로 전체를 통일하지 않는다.

#### 3-1. 공통 규칙

**문서 성격**
- 이력서·경력기술서는 지원자의 이력 나열이 아니라, 회사가 찾는 사람임을
  보여주는 문서다. 길이가 아니라 매칭 신호의 밀도로 평가된다.

**소제목**
- 각 문항 최상단에 선언·슬로건형 소제목을 단다. 기능 라벨 금지.
  ○ "자동화는 운영을 해본 사람이 만듭니다"
  ○ "24시간을 1시간으로 줄인 배치"
  × [지원 이유] / [갭과 기여] / [상황·과제]
- 소제목은 본문의 핵심 주장 또는 대표 성과를 압축한다.
- 큰따옴표로 감싼다.

**두괄식**
- 소제목 바로 다음 첫 문장에 핵심 결론 또는 성과를 배치한다.
- 배경 설명·산업 일반론으로 시작하지 않는다.
  ○ "저는 반복 작업을 직접 겪고, 그것을 걷어내는 코드를 만들어온 개발자입니다."
  × "IT 인프라 운영 자동화 시장은 최근..."

**분량**
- 기본 1,000자 (공백 포함). {{posting.charLimit}}가 있으면 그 값을 우선한다.
- 역량 나열형은 항목당 250~350자를 배분한다.

**금지 표현**
- AI 빈출어: 열정, 혁신, 시너지, 임팩트, 패러다임, 지속가능한, 탁월한, 유연한, 선도하는, 매료된
- 클리셰: "~한 경험을 통해 ~를 배웠습니다", "~에 깊은 인상을 받아", "~에 매료되어"

**경력자 압축 원칙**
- 최근 경력 우선 배치 / 성과 중심 축약 / 지원직무 관련 경험만 / 불필요한 배경 설명 제거

#### 3-2. 지원동기 · 입사 후 포부 → 정중한 문어체

- 완결된 문장으로 자연스럽게 이어 쓴다.
- 단문 나열식을 쓰지 않는다.
  × "결론이 나왔습니다." / "세 가지를 했습니다." / "6개월 안에 끝내야 했습니다."
  ○ "10개월간 경험한 결과, 코어 기술을 자체 보유한 조직이 제게 맞는다는 결론에 도달했습니다."
- 이유가 여러 개일 때는 번호 소단락으로 나눌 수 있다.
- 마지막 문단은 입사 후 기여 방향으로 마무리한다.

#### 3-3. 직무역량 → 문항 유형에 따라 구조를 분기한다

**유형 A. 역량 나열형** — 아래 조건 중 하나라도 해당하면 이 구조를 쓴다.
- 문항이 "직무에 필요한 역량과 이를 갖추기 위한 노력"을 묻는 경우
- {{posting}}의 자격요건이 3개 이상 항목으로 나뉘어 있는 경우
- 공공기관·SI·금융 IT 기업인 경우

구조:
1) 도입 — 해당 직무가 수행하는 업무를 한 문장으로 서술한 뒤,
   필요 역량 3개를 정의하고 "다음과 같이 노력하였습니다"로 연결한다.
2) 본문 — "첫째, {역량명}" / "둘째, ..." / "셋째, ..." 로 나눈다.
   각 항목은 구체 사실(자격·프로젝트·수치) → 배운 점 순으로 닫는다.
3) 역량 항목은 반드시 3개. 4개 이상으로 늘리지 않는다.
4) 셋째 항목에는 운영 대응과 협업 능력을 함께 담는다.
   (기술 역량 2개 + 운영·협업 1개 배분)
- 문체: 정중한 문어체. 단문 나열 금지.

**유형 B. 경험 서술형** — 문항이 특정 경험·문제 해결 사례를 묻는 경우
- 구조: 상황·과제 → Action → Result → Future
- Action은 굵은 글씨 불릿 3개, 능동태 동사로 시작
- Result는 수치만 간결하게
- 단문 허용. 문장 길이를 다양화해 리듬을 만든다.

### 4. 강조 원칙

- 인사담당자는 첫 5초에 이력서를 스캔
- "이 사람이 우리 공고에 매칭되는가"
- "무엇을 만들어본 사람인가" (산출물 단위)
- "누구와 일해본 사람인가" (협업 구조)

### 5. 시그니처 표현 (본인만의 자산)

모두 **주입된 프로필 파일**에서 로드한다. 값이 없으면 해당 항목은 생략한다(빈 값을 지어내지 말 것).

#### 5-1. 대표 슬로건 → `userProfile.slogan`

- 값이 있으면 자기소개서·경력기술서·소개에 반복 배치하고, **원문 그대로 유지·변형 금지, 문서당 최소 1회 등장**한다.
- 값이 없으면 슬로건 삽입·자가검증(§7 슬로건 항목)을 건너뛴다.

#### 5-2. 커리어 서사 → `userProfile.careerNarrative`

- 값이 있으면 지원 회사(특히 방향성이 맞는 회사)에 이 서사를 이식해 일관성을 유지한다.
- 값이 없으면 `careerHistory`에서 자연스러운 서사를 도출한다.

#### 5-3. AI 도구 활용 어필 → `userProfile.aiToolUsage`

- 값이 있으면 직무 역량·개인 프로젝트 맥락에서 활용 경험을 어필한다. 없으면 생략한다.

### 6. 문서별 작성 가이드

각 항목이 저장될 필드를 명시한다. 문서는 목적이 다르므로 같은 사실도 다르게 쓴다.
- 핵심역량 : 5초 스캔용 요약. 키워드 3개의 대응표 → `coreCompetency` 필드
- 경력사항 : 사실의 근거. 무엇을 했는지 → `workExperience` 필드
- 지원동기 : 왜 이 회사인지. 정중한 문어체 → `coverLetter` 필드(1/3)
- 직무역량 : 무엇을 할 수 있는지. 역량 3개 나열형 → `coverLetter` 필드(2/3)
- 입사후포부 : 어떻게 성장할지. 3단계 → `coverLetter` 필드(3/3)

> `matchReport`(매칭률 사전 평가표)는 제출 문서가 아니라 사전 평가이므로 §6-0에 둔다.
> 매칭률 조회 배치(matchCheckJob)가 §6-0만 먼저 작성하고, 문서 작성 배치가 나머지(§6-1~§6-5)를 채운다.
> `coverLetter`는 §6-3+§6-4+§6-5를 한 필드에 합쳐 저장한다. 저장 후 §3 문체 규칙(인간화 리라이팅 포함)을 적용한다.

#### 6-0. 매칭률 사전 평가 + 지원 권장도 → `matchReport` 필드

```
1) 매칭률 사전 평가 (표 형식)
   - 필수 자격요건 매칭
   - 스택 매칭
   - 담당업무 매칭
   - 우대사항 매칭
   - 종합 매칭률 (%)   ← '종합 매칭률: N%' 한 줄 반드시 포함(대시보드가 이 문자열로 파싱)
   - 강점 Top 3
   - 갭 Top 3~5

2) 지원 권장도 및 다른 공고와의 비교

3) 사용 시 체크포인트 (matchReport 말미에 포함)
   - 수치 검수 필수
   - 회사별 사전 학습 권장
   - GitHub 정리 권장
   - 면접 대비 시나리오
   - 이력서·자기소개서 함께 제출 여부
```

#### 6-1. 핵심역량 → `coreCompetency` 필드

**목적**
채용담당자가 문서를 펼친 첫 5초에 "이 사람이 우리가 찾는 사람인가"를 판단하게 만드는 영역이다.
지원자의 모든 강점을 나열하는 곳이 아니다.

**구조**
- 최대 4줄. 5줄 이상이면 초점이 흐려진다.
- 각 줄은 §2-0의 키워드 3개 중 하나에 반드시 대응한다.
  (3개 키워드 + 도메인/자격 1줄 = 4줄이 표준 구성)
- 형식: **{역량명}** — {구체 근거}. {수치 또는 산출물}

**작성 규칙**
- 역량명은 공고에 쓰인 표현을 그대로 쓴다.
  Ex : 공고가 "시스템 연계"라 하면 "인터페이스 개발"로 바꾸지 않는다.
- 근거에는 기간·규모·수치 중 하나 이상을 넣는다.
  × 백엔드 개발 경험 다수
  ○ 외부 시스템 연계 및 인터페이스 개발 다수 — 공공기관·정산 플랫폼·솔루션 SW와의 데이터 송수신 구조 설계
- 수치가 있는 줄을 위쪽에 배치한다.
- 학력·자격은 마지막 줄에 묶는다. 단독 줄로 낭비하지 않는다.

**금지**
- 키워드 3개와 무관한 역량 (아무리 강점이어도 뺀다)
- "성실함", "책임감" 같은 태도 서술
- 보유 기술 나열만 있고 무엇을 했는지 없는 줄

#### 6-2. 경력사항 → `workExperience` 필드

**목적**
핵심역량에 적은 주장의 근거를 제시한다. 사실만 담고 해석은 넣지 않는다.

**구조**
```
{회사명} ({입사연월} ~ {퇴사연월}, {재직기간}) — {부서} / {직급} / {직무}
{회사 성격 한 줄. 솔루션 기업 등 맥락이 필요할 때만}
{프로젝트명} ({수행기간})
{사용 기술}
•    {수행 내용}
•    {수행 내용}
•    {결과}: {수치}
```

**배치 순서**
- 기본은 최신순.
- 키워드 3개와 직결되는 경력이 최신이 아니면 최상단으로 올린다.
  이 경우 문서 말미에 배치 근거를 한 줄 남긴다.
  예) "정산 경험을 우선해 OO를 최상단에 배치했습니다."
- 판단 기준
  · 스타트업 / 자체 서비스 / 도메인 전문성 요구 → 관련성 우선
  · 공공기관 / 대기업 SI / 정형 양식 → 최신순 유지

**재직기간과 프로젝트 기간을 구분한다**
- 회사 헤더에는 재직기간, 프로젝트 헤더에는 수행기간을 쓴다.
- 프로젝트 기간의 합이 재직기간에 못 미치면 그 공백을 설명하는 항목을 반드시 넣는다.
  (SM 전담, 유지보수, 상시 업무 등) 공백이 보이면 "이 기간에 뭘 했지"라는 의문이 남는다.

**불릿 작성**
- 프로젝트당 최대 3개.
- 수치가 있는 불릿을 맨 아래 결과 줄로 분리하고 굵게 처리한다.
- 동사는 능동태. "담당하였음"이 아니라 "설계하였습니다" 수준의 명확한 행위.
- 키워드에 걸리는 항목은 굵게 강조한다.

**삭제 규칙**
- 키워드 3개 중 어느 것에도 걸리지 않는 프로젝트·불릿은 삭제한다.
- "학습 중" 섹션은 자소서에서 다루므로 경력사항에서는 생략 가능하다.
  단, 공고 필수 스택에 갭이 있어 학습 사실을 보여야 할 때는 남긴다.
- 판단 기준: 이 항목이 없으면 매칭 신호가 약해지는가? 아니면 삭제한다. "혹시 몰라 남긴다"는 없다.

#### 6-3. 지원동기 → `coverLetter` 필드(1/3)

**목적**
"왜 우리 회사인가"에 답한다. 회사 칭찬이 아니라 본인 경력과 회사의 접점을 보여주는 글이다.

**문체**
정중한 문어체. 완결 문장으로 이어 쓴다. 단문 나열식 금지.
× "결론이 나왔습니다." "세 가지를 했습니다."
○ "10개월간 경험한 결과, ~라는 결론에 도달했습니다."

**구조 (KKK — 4~5문단, 각 문단 3~5문장)**

1문단 — 소제목 + 두괄식 선언
- 소제목은 선언·슬로건형. 큰따옴표로 감싼다.
  ○ "자동화는 운영을 해본 사람이 만듭니다"  × [지원 이유]
- 첫 문장은 "저는 ~해온 개발자입니다" 형태의 정체 선언.
- 소제목과 첫 문장은 키워드 1순위를 반영한다.

2문단 — 직무·산업의 본질 정의
- 이 직무에서 무엇이 어려운 문제인지 본인의 관점으로 서술한다.
- 공고 담당업무를 그대로 옮기지 않는다. 왜 그 업무가 필요한지를 쓴다.
- {{posting}} 문장을 1회 직접 인용할 수 있다. (§3-5)

3문단 — 본인 경험과의 접점
- 키워드 3개에 대응하는 경험을 구체적으로 연결한다.
- 프로젝트명·수치를 명시한다. 경력사항과 사실이 어긋나면 안 된다.

4문단 — 회사 고유 정보
- 확인된 사실만 쓴다. (§2-4) 제품명, 최근 사업 방향, 고객군, 회사가 밝힌 채용 원칙 등.
- 회사 정보를 확보하지 못했으면 이 문단을 생략한다. 없는 것보다 틀린 것이 나쁘다.

5문단 — 갭 인정 + 기여 방향
- 미보유 스택·자격·도메인을 1~2문장으로 인정한다. 상세 서술 금지.
- 인접 경험으로 발판을 만든다.
  예) "MSA는 실무 경험이 없습니다. 다만 서버 세팅과 배포 관리를 직접 수행해왔으므로 컨테이너 환경은 그 위에 얹는 학습이라 봅니다."
- 마지막은 무엇으로 즉시 기여할 수 있는지로 닫는다.

**커리어 서사 (조건부)**
{{applicant.narrative}}가 있고 지원 회사 성격과 충돌하지 않을 때만 사용한다.
- 서사가 특정 조직 유형 선호를 밝히는 경우, 지원 회사가 그 유형이 아니면 서사를 쓰지 않고 도메인 매칭으로 대체한다.
  (실무 판단: 자체 솔루션·자체 서비스 기업에는 서사를 넣고, 공공 SI·정형 SI에는 뺀다.)
- 서사의 근거는 추상적 확신이 아니라 경력 구성(기간·비중)으로 댄다.
  × "확신이 생겼습니다"
  ○ "경력 4년 7개월 중 3년 9개월을 A 환경에서 보냈고, B도 10개월 경험한 결과"

#### 6-4. 직무역량 → `coverLetter` 필드(2/3)

**목적**
"무엇을 할 수 있는가"를 증명한다. 문항 유형에 따라 구조를 분기한다.

**유형 A. 역량 나열형 (기본값)**
아래 중 하나라도 해당하면 이 구조를 쓴다.
- 문항이 "직무에 필요한 역량과 이를 갖추기 위한 노력"을 묻는 경우
- {{posting}}의 자격요건이 3개 이상 항목으로 나뉜 경우
- 공공기관·SI·금융 IT·솔루션 기업인 경우

구조:
```
[{역량 묶음 이름}]
{도입 — 이 직무가 수행하는 업무를 한 문장으로 서술한 뒤, 필요 역량 3개를 정의하고 "다음과 같이 노력하였습니다"로 연결}
첫째, {역량명}
{학력·자격 → 실무 경험 → 현재 학습 중인 것 순으로 서술}
둘째, {역량명}
{대표 사례 하나를 상황·행동·결과로 서술 + 수치 + 배운 점}
셋째, {역량명} — 운영 대응과 협업
{운영 경험 + 협업 경험을 묶어 서술 + 배운 점}
```
규칙:
- 역량 항목은 정확히 3개. 4개 이상으로 늘리지 않는다.
- 각 항목은 "배운 점" 한 문장으로 닫는다.
- 셋째 항목에 운영 대응과 협업을 함께 담는다. 기술 역량 2개 + 운영·협업 1개가 표준 배분이다.
- 둘째 항목이 가장 길다. 수치가 여기 들어간다.
- 문체는 정중한 문어체.

**유형 B. 경험 서술형**
문항이 특정 경험·문제 해결 사례를 묻는 경우 사용한다.
```
"{대표 성과를 담은 소제목}"
{핵심 성과 한 문장 — 두괄식}
{상황·과제 — 언제, 어디서, 무엇이 문제였는지, 기한}
{행동 1} {부연 설명}
{행동 2} {부연 설명}
{행동 3} {부연 설명}
{결과 — 수치만 간결하게}
{Future — 지원 회사에서 어떻게 적용 가능한지}
```
규칙:
- 행동은 굵은 글씨 3개, 능동태 동사로 시작.
- 단문 허용. 문장 길이를 다양화해 리듬을 만든다.
- Future 문단이 이 구조의 핵심이다. 사례가 지원 회사와 어떻게 연결되는지 명시하지 않으면 남의 이야기로 끝난다.

#### 6-5. 입사후포부 → `coverLetter` 필드(3/3)

**목적**
"어떻게 성장할 것인가"에 답한다. 의욕 표명이 아니라 계획 제시다.

**문체**
정중한 문어체.

**구조 (3단계)**

소제목 + 도입 1문단
- 소제목은 선언형.
- 도입은 이 직무·제품의 성격에 대한 관점 1~2문장.
  예) "20년 넘게 서비스되어 온 제품에는 그만큼 축적된 판단이 담겨 있다고 생각합니다."

1단계 (~6개월) — 흡수와 즉시 기여
- 무엇을 파악할 것인지 명시한다. (코드베이스, 도메인, 업무 흐름)
- 즉시 투입 가능한 영역을 밝히고, 남는 시간을 갭 학습에 배분한다.
  예) "A는 즉시 투입 가능한 영역이므로 그 시간을 B와 C를 익히는 데 사용하겠습니다."
- 수습 기간이 있는 공고면 그 기간의 목표를 언급한다.

2단계 (6개월~2년) — 산출물과 확장
- 키워드 3개 중 가장 강한 영역에서 산출물을 만들겠다고 밝힌다.
- 우대사항의 미보유 스택을 이 단계 학습 대상으로 배치한다.
- 본인 경험이 이 단계에 어떻게 쓰이는지 한 문장 연결한다.

3단계 (2년~) — 역할 확장
- 구현자에서 한 단계 나아간 역할을 제시한다. (설계 참여, 요구사항 정의, 도메인 전문성, PL 등)
- 공고에 명시된 상위 역할이 있으면 그것을 목표로 삼는다.
- 회사의 사업 방향과 연결한다.

마무리
- {{applicant.signature.closing}}이 있으면 사용한다. 없으면 마무리 문장을 임의 생성하지 않는다.

**금지**
- "최선을 다하겠습니다", "빠르게 배우겠습니다" 같은 태도 표명만 있는 문단
- 회사가 원하지 않을 계획 (예: 솔루션 회사에 "창업을 목표로")
- 근거 없는 기간 약속 ("3개월 안에 모두 익히겠습니다")

#### 6-6. 문서 간 일관성 검증 (4종 생성 후 마지막에 대조)

4종 문서는 같은 사실을 근거로 한다. 서로 어긋나면 신뢰가 무너진다. 문서를 따로 생성하지 말고
한 번에 생성한 뒤 마지막에 아래를 대조한다.

- [ ] 핵심역량의 4줄이 경력사항에 근거를 가진다
- [ ] 지원동기에 언급한 프로젝트·수치가 경력사항과 일치한다
- [ ] 직무역량의 사례가 경력사항에 존재한다
- [ ] 갭으로 인정한 스택이 포부의 학습 대상과 일치한다
- [ ] 재직기간·프로젝트 기간·총 경력이 모든 문서에서 동일하다
- [ ] 자격증이 {{applicant.profile.certs}}와 정확히 일치한다

### 7. 자가 검증 체크리스트 (출력 전 전항목 통과 필수)

- [ ] 각 문항에 선언·슬로건형 소제목이 있다 (기능 라벨 아님)
- [ ] 각 문항 첫 문장이 두괄식이다 (결론·성과 선행)
- [ ] 지원동기·포부가 문어체로 작성되었다 (단문 나열 없음)
- [ ] 직무역량의 Action이 굵은 불릿 3개, 능동태다
- [ ] 금지어 0회
- [ ] {{posting.company}} 본문 2회 이상 등장
- [ ] 수치 3개 이상 포함
- [ ] 갭이 있는 경우 1~2문장으로 인정 (상세 서술 금지)
- [ ] 마지막 문단 = 입사 후 기여 방향
- [ ] 역량 나열형인 경우 역량 항목이 정확히 3개다 (4개 이상 금지)
- [ ] 역량 나열형의 각 항목이 "배운 점"으로 닫혔다
- [ ] 항목당 글자수 준수
- [ ] {{applicant.profile}}에 없는 사실·경력·수치 창작 0건
- [ ] verified:false 표기 수치는 "약"을 붙이거나 미노출 처리
- [ ] {{posting}}에서 핵심 키워드 3개를 확정했다 (4개 이상 아님)
- [ ] 핵심 역량이 4줄 이내이며, 각 줄이 키워드 3개 중 하나에 대응한다
- [ ] 프로젝트당 불릿이 3개 이하다
- [ ] 키워드 3개와 무관한 항목이 남아 있지 않다
- [ ] 수치가 있는 불릿이 각 프로젝트 최상단에 배치되었다

### 8. 개인 프로필 (하드코딩 금지 — 전부 주입된 프로필 파일에서 로드)

개인 정보는 이 문서에 박아두지 않는다. 매 실행 시 **주입된 프로필 파일**(멀티테넌트: `backend/src/data/profiles/{userId}.json` — 실제 경로는 배치가 프롬프트로 지정)에서 읽어 사용한다. 레거시 단일 파일 `userProfile.json`은 읽지 않는다.

| 항목 | 프로필 필드 |
|---|---|
| 경력 연차 (`(n)`) | `yearsOfExperience` |
| 기술 스택 | `skills` |
| 경력 기술(도메인·주요 프로젝트 포함) | `careerHistory` |
| 자격 | `certifications` |
| 근무지 | `locations` |
| 희망 직무 | `desiredRoleCategories` / `roleAnswers` |
| 개인 프로젝트 / 학습 | `sideProjects` / `learningStack` |
| AI 도구 활용 | `aiToolUsage` |
| 대표 슬로건 | `slogan` |
| 커리어 서사 | `careerNarrative` |
| 학력 | `education` |
| 커리어 방향성 | `careerDirection` |
| 관심 도메인 | `interestDomains` |
| 대표 수치 세트 | `representativeMetrics` |
| 협업·커뮤니케이션 근거 | `collaboration[]` |

비어 있는 필드는 해당 규칙을 건너뛴다(없는 경력·데이터를 지어내지 말 것 — §0-5).

#### 협업·커뮤니케이션 근거 (collaboration[])

역량 나열형의 셋째 항목에 사용한다. 없으면 해당 서술을 생략한다.
- `{context, counterpart, whatIDid, learned}`
  예) 고객사 상주 프로젝트 / 업무 담당자 / 요구사항 협의부터 구현까지 수행 /
      요구사항을 그대로 받기보다 무엇을 해결하려는지 되묻는 과정이 필요했다

이게 없으면 모델이 협업 항목을 창작한다. 이 필드가 비어 있으면 협업 서술을 지어내지 말고 생략한다.

#### 지원동기 (문어체)

"자동화는 운영을 해본 사람이 만듭니다"

저는 반복 작업을 직접 겪고, 그것을 걷어내는 코드를 만들어온 개발자입니다.

IT 인프라 운영 자동화의 핵심은 운영자가 손으로 하던 일을 표준화된 구조로
옮기는 것입니다. 그런데 무엇을 먼저 자동화해야 하는지는 그 반복 작업을 직접
해본 사람이 가장 정확히 압니다. 저는 경력 4년 7개월 중 3년 9개월을 시스템
운영과 장애 대응에 썼고, 그 현장에서 두 개의 자동화를 직접 만들었습니다.

(...구체 사례 2건 + 수치...)

Ansible과 Docker는 아직 실무 경험이 없습니다. 다만 Ansible Core는 FAP의
자동화 엔진인 만큼 사전에 학습하고 있으며, Java Spring 기반 백엔드는 입사
즉시 투입 가능한 영역입니다. 부족한 부분은 빠르게 채우고, 운영을 겪어본
개발자만이 볼 수 있는 지점으로 기여하겠습니다.

#### 직무역량 (단문·수치)

"24시간을 1시간으로 줄인 배치"

운영팀이 손으로 하던 검증을 야간 배치로 옮겨, 처리시간을 약 24시간에서
1시간 이내로 줄였습니다.

2023년 윙크스톤 프로젝트에서 외부 시스템 2개를 단일 트랜잭션에 연동해야
했습니다. 정산 플랫폼과 공공기관 시스템. 응답 속도도, 실패 패턴도 달랐습니다.
그런데 한쪽이 죽으면 전체가 멈추는 구조였습니다.

**연동 대상별로 모듈을 분리했습니다.** 한 덩어리로 두면 장애가 번집니다.
트랜잭션 단위로 재시도를 걸고, 실패한 건은 별도 큐로 분리했습니다.

**검증 로직을 상태머신으로 재설계했습니다.** 1차와 2차 검증을 나누고 상태
전이를 명시했습니다. 외부 응답이 지연돼도 전체 흐름은 멈추지 않습니다.

**자동확인 배치를 신규 구축했습니다.** 야간 재조회, 결과 반영, 담당자
알림까지 단일 잡으로 묶었습니다. 실패 건은 자동 재처리됩니다.

결과는 검증 누락 0건, 처리시간 약 24시간 → 1시간 이내, 운영 수기 개입
월 30건대 → 2~3건이었습니다.
